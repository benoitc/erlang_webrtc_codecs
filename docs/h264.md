# H.264

H.264 is the codec to use with peers that have no VP8, such as some phones,
SIP gateways and hardware. Use this plugin to get the H.264 video of a peer
as pictures, or to send pictures you produce. It runs on OpenH264, so the
library has to be there when you build.

## Build with OpenH264

[Set up on your system](install.md) has the packages to install for each
system. Then:

```sh
rebar3 compile
```

Check that the codec is there:

```erlang
[#{implementation := <<"OpenH264 ", _/binary>>}] = [C || #{name := <<"H264">>} = C <- webrtc_codecs:available()].
```

## Receive

```erlang
{ok, Pc} = webrtc:new_peer_connection(#{
    frames => true,
    codec_plugins => #{video => {webrtc_codecs, #{}}}
}),

receive
    {webrtc, Pc, {decoded, Mid, #{format := i420, width := W, height := H} = Picture}} ->
        show(Picture);
    {webrtc, Pc, {decoded, Mid, #{dropped := Reason}}} ->
        logger:info("frame dropped: ~p", [Reason])
end.
```

## Send

erlang_webrtc offers VP8 first. To send H.264, put it first in the codecs
you offer:

```erlang
{ok, Video} = webrtc:prefer_codec(<<"H264">>, webrtc:default_codecs(video)),
{ok, Pc} = webrtc:new_peer_connection(#{codecs => #{video => Video}}),
{ok, _} = webrtc:add_transceiver(Pc, video, #{frames => true, codec_plugin => {webrtc_codecs, #{}}}),

ok = webrtc:send_media(Pc, Mid, #{
    format => i420,
    width => 640,
    height => 480,
    y => Y,
    u => U,
    v => V,
    timestamp => Ts
}).
```

## Follow the network

```erlang
receive
    {webrtc, Pc, {bandwidth_estimate, Bps}} ->
        ok = webrtc:set_target_bitrate(Pc, Mid, Bps)
end.
```

The estimate is for the whole connection: give each encoder its share. A
key frame the peer asks for and a limit the peer puts on the stream reach
the encoder without you.

## Options

| Option | Default | Meaning |
|---|---|---|
| `bitrate` | from the picture size | Bitrate of the encoder at start, in bits per second |
| `min_bitrate` | `30000` | Lowest bitrate the encoder is given |
| `max_bitrate` | none | Highest bitrate the encoder is given |
| `keyframe_interval` | `3000` | Most frames between two key frames |
| `threads` | from the picture size | Threads of the encoder |
| `max_pixels` | `8294400` (3840 x 2160) | Largest picture the decoder accepts |
| `max_nal_size` | `1100` with `packetization-mode=0`, none otherwise | Largest NAL unit the encoder writes, in bytes, from 500 to 65536 |

## Notes

- The encoder writes constrained baseline, which a peer that negotiated
  baseline, main, extended or high can decode. A `profile-level-id` of
  another profile, or one that is not six hexadecimal digits, makes the
  plugin refuse to start (`{unsupported_profile, Value}`).
- The level in `profile-level-id` is not enforced: a larger picture is
  encoded and the stream states its real level. Keep the picture size and
  the bitrate within what the peer announced.
- With `packetization-mode=1` or `2` a picture is one slice and
  erlang_webrtc cuts it into packets. With `packetization-mode=0`, which is
  also what a format without the parameter means, a packet holds one NAL
  unit: the encoder cuts the picture into slices of at most `max_nal_size`
  bytes. Set `max_nal_size` yourself to get slices in the other modes.
- The decoder takes baseline, main and high, 8 bit 4:2:0.
- A frame is an access unit in Annex B. A key frame is one with an IDR
  slice, and the encoder puts the parameter sets in front of each.
- Width and height have to be even when you encode: OpenH264 would cut the
  last column or line, so an odd size is an error.
- A frame that cannot be decoded gives `#{dropped => Reason, timestamp =>
  Ts}`, and so does every frame after it until a key frame
  (`waiting_for_keyframe`). Errors are not concealed.
- Every sequence parameter set a peer sends is read before OpenH264 sees
  it, in a key frame or not. One that declares more than `max_pixels`, on
  the size as coded, makes the frame dropped (`too_large`). One that cannot
  be read, of a profile other than baseline, main, extended or high, or a
  subset set, makes it dropped as `unsupported_parameter_set`.
- OpenH264 does not tell the quantizer, so `qpSum` is not reported.
- OpenH264 is BSD licensed. The H.264 patent licence Cisco pays for covers
  the binaries Cisco distributes, not one you or your distribution built.
